## What Was Delivered

M1.0 delivers the **complete core pipeline** for Hebrew book layout:

```
JSON Input → HarfBuzz Shaping → Line Breaking → Two-Column Layout → PDF Output
```

### Components Implemented

#### 1. **Line Breaking** (`src/line-breaking/greedy-breaker.ts`)
- Greedy algorithm (simplest viable approach)
- Word-level breaking with configurable word spacing
- Optional mid-word breaking at glyph boundaries
- 12 comprehensive tests

#### 2. **Two-Column Layout** (`src/layout/two-column-layout.ts`)
- RTL-aware column distribution (right column fills first)
- Configurable margins, column gap, line height
- Automatic page overflow handling
- 15 comprehensive tests

#### 3. **Integration Layer** (`src/core/layout-engine.ts`)
- Orchestrates entire pipeline
- Multi-page document generation
- Complete positioning information (X, Y for every glyph)
- 15 integration tests

#### 4. **PDF Rendering** (`src/rendering/pdf-renderer.ts`)
- PDFKit integration with Hebrew font support
- Word-level rendering (Alternative A from ADR-004)
- Multi-page PDF generation
- 5 integration tests + 3 E2E tests

## Key Design Decisions (ADRs)

### ADR-004: Rendering Strategy
**Chosen:** Alternative A (Word-level PDFKit rendering)

**Rationale:**
- M1.0 is MVP - simplicity over pixel-perfection
- PDFKit's `text()` method handles complex font rendering
- Defers glyph-level rendering (Alternative B) to M2

**Tradeoff:**
- Double shaping (HarfBuzz + PDFKit internal)
- Good enough for M1.0, will optimize in M2

### ADR-005: BiDi Deferral
**Decision:** Hebrew-only in M1.0, full BiDi support in M1.1

**Rationale:**
- BiDi library APIs complex (UAX #9 implementation non-trivial)
- Hebrew RTL base direction sufficient for M1.0 core pipeline
- Estimated 1 week additional effort for M1.1

---

## What M1.0 Does NOT Include

❌ **BiDi Support** (deferred to M1.1)
- No Hebrew + Latin mixed text
- No digit reordering
- Hebrew-only RTL assumption

❌ **Justification** (deferred to M2)
- No inter-word spacing adjustment
- No kashida insertion
- Lines use natural word spacing only

❌ **Hyphenation** (deferred to M2)
- No mid-word breaking with hyphens
- Optional glyph-boundary breaking only

❌ **Advanced Typography** (deferred to M3+)
- No widow/orphan control
- No baseline grid
- No column balancing

## Lessons Learned

### ✅ What Went Well
1. **Test-first approach** - All 88 tests passing gives confidence
2. **Pragmatic decisions** - Chose simplicity (word-level rendering) over perfection
3. **Clear ADRs** - Documented key decisions (ADR-004, ADR-005)
4. **Performance baseline** - 64k words/sec establishes good baseline

### ⚠️ Challenges
1. **PDFKit baseline positioning** - Y-coordinate confusion (top vs baseline)
2. **Column width calculations** - Off-by-one errors in margin arithmetic
3. **BiDi complexity** - Library APIs more complex than expected

### 🔄 Would Do Differently
1. **Earlier BiDi investigation** - Would have caught complexity sooner
2. **More realistic test data** - Mock word widths initially too small
3. **PDF inspection tools** - Would benefit from automated PDF content verification
