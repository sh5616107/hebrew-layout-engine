# Hebrew Layout Engine POC: Vivliostyle vs Typst Evaluation

A proof-of-concept comparing two layout engines (Vivliostyle HTML/CSS and Typst) against 13 requirements for Hebrew religious book layout. The evaluation concludes that neither engine is production-ready as-is, with both requiring 350-1000 LOC of workarounds. The report documents these gaps with code-level evidence and estimates custom development effort.

Genesis 1 text with authentic nikud and teamim was used as sample content. Both engines successfully generated PDFs. The work includes a complete document model, two adapters (HTML/CSS and Typst), functioning build pipelines, and a determinism test. Critical gaps are documented in adapter source comments with references to upstream issues.

**Watch for:** No PNG visual evidence files exist (PDF-to-PNG conversion tools unavailable), so 8 of 13 requirements remain marked UNVERIFIED despite being implemented. Baseline grid alignment between columns failed for Vivliostyle (confirmed), full-width footnotes failed for Typst (confirmed). The "window below opening words" feature was not implemented in either adapter.

**Verdict**: NEEDS_CHANGES

## High-level view

Both PDFs were successfully generated and determinism tests completed, though byte-level comparison failed due to PDF metadata timestamps. The document model in sample.json uses authentic Genesis 1 text with nikud and teamim from Mechon-Mamre, includes three footnotes (one intentionally long), and defines opening-word flags for visual treatment. Both adapters read the same model and translate to engine-specific formats without embedding layout logic in the source data.

Vivliostyle's baseline grid alignment between columns is a documented engine limitation (issue #1157), requiring 200-400 LOC of custom CSS Grid or JavaScript layout to work around. The opening-word window feature (empty space below bold words) wasn't implemented in either adapter, with Vivliostyle requiring shape-outside plus JavaScript measurement (150-250 LOC) and Typst requiring custom placement functions (100-200 LOC).

Typst's footnote handling in two-column layouts places notes at the bottom of each column rather than in a full-width area above both columns, a known forum-documented limitation requiring 300-500 LOC of manual footnote collection. Typst also lacks a text-align-last equivalent for centering only the final line of paragraphs, requiring 150-300 LOC of custom show rules.

The David font (Windows system) was used for both engines, supporting nikud but with limited teamim coverage. The report recommends Ezra SIL as a drop-in replacement requiring zero code changes. No PDF-to-PNG conversion tools were available during testing, leaving visual verification incomplete—8 requirements are marked UNVERIFIED despite being implemented in code.

## Document model and sample data

The sample.json file defines a complete document model following the schema from SPEC.md section 4. It includes meta (title, author), styles (body, heading1, heading2, footnote with font, size, line-height, alignment), pageSpec (B5 dimensions in points, margins, columns, baselineGrid), sections containing blocks, and a notes array with three footnotes.

Text content is authentic Genesis 1:1-10 from Mechon-Mamre with nikud and teamim (בְּרֵאשִׁ֖ית בָּרָ֣א אֱלֹהִ֑ים...). The first body paragraph (block-2) has an opening flag requesting 3 bold words with a 2-line window below. Block-7 references note-3, a 150-word footnote deliberately long to test cross-page continuation.

The model is engine-agnostic. All layout semantics live in the JSON structure, not in adapter logic. Both to-html-css.js and to-typst.js read the same input and translate to their respective output formats without embedding layout decisions.

## Adapter implementation and limitation documentation

Both adapters follow the same structure: read sample.json, iterate blocks, generate engine-specific markup for headings, paragraphs, footnotes, and running headers. Gematria numbering (א, ב, ג... with special cases טו for 15 and טז for 16) is implemented in JavaScript for Vivliostyle and Typst functions for Typst.

Engine limitations are documented directly in adapter source code with comments prefixed VIVLIOSTYLE-LIMITATION and TYPST-LIMITATION. These comments cite specific upstream issues and forum threads. Vivliostyle's to-html-css.js line 256 documents baseline grid limitation with a link to issue #1157. Line 248 documents the shape-outside challenge for opening-word windows. Typst's to-typst.js line 82 documents the lack of last-line centering support, line 134 documents window implementation complexity, and line 171 documents the per-column footnote limitation with forum link.

The opening-word window feature (requirement f) was not implemented in either adapter. Bold emphasis works, but the empty rectangular space below the bold words is missing. Vivliostyle would need CSS shape-outside combined with JavaScript width measurement of the Hebrew text; Typst would need custom placement or layout functions. Both are complex enough to defer to post-POC work.

## PDF generation and determinism testing

Both engines successfully generated PDFs. Vivliostyle produced 24,645-byte output, Typst produced 36,602-byte output. The vivliostyle/ directory contains generated index.html and style.css; the typst/ directory contains main.typ.

Determinism tests ran each engine twice and compared SHA256 hashes. Both failed: vivliostyle-run1.pdf and vivliostyle-run2.pdf have different hashes, as do typst-run1.pdf and typst-run2.pdf. The cause is PDF metadata (creation timestamp, modification timestamp, or embedded UUIDs). Visual content is likely identical, but binary comparison fails. The workaround is to strip PDF metadata before hashing or compare rendered pixels rather than bytes.

## Requirements matrix and evidence gaps

RESULTS.md includes a 13-row matrix rating each requirement for both engines. Ratings are PASS (fully working), PARTIAL (works with caveats), FAIL (doesn't work), UNVERIFIED (implemented but no PNG to inspect), or NOT IMPL (not in sample scope).

8 requirements are UNVERIFIED: page size (a), two columns (c), column balancing (d), baseline grid for Typst (e), footnote positioning (h), footnote same-page (i), footnote continuation (j), and running headers (k). These are implemented in the adapters and PDFs exist, but no PNG files were generated to visually verify them. The cause is missing PDF-to-PNG conversion tools (ImageMagick or Poppler).

The confirmed failures are: Vivliostyle baseline grid (e), both engines' opening window (f), Typst last-line centering (g), Typst full-width footnotes (h), and both engines' determinism (m). The confirmed partials are: Hebrew rendering with limited teamim support (b), Vivliostyle last-line centering which may also center column-break lines (g).

EVIDENCE.md maps each requirement to specific files and verification procedures. It documents the exact PNG filenames expected, the PDF pages to inspect, the measurement method, and pass criteria. For example, requirement (e) specifies overlaying a 14pt grid and measuring vertical positions of corresponding lines in each column, with tolerance ±0.5pt.

## Font selection and teamim coverage

Both adapters specify "Ezra SIL" in the document model styles but fall back to "David" (Windows system font) if Ezra SIL is not installed. David supports Hebrew with nikud (U+05B0–U+05C7) but has limited teamim (cantillation marks, U+0591–U+05AF) coverage. The Genesis text includes authentic teamim from Mechon-Mamre, so visual verification would show whether marks render correctly.

Switching to Ezra SIL or Taamey David CLM requires zero code changes—only installing the font and regenerating PDFs. Ezra SIL is SIL OFL licensed (permissive, allows embedding), based on Biblia Hebraica Stuttgartensia typography, and designed specifically for Biblical Hebrew with full teamim support.

RESULTS.md requirement (b) is marked PARTIAL for both engines pending visual inspection with Ezra SIL installed. If teamim render correctly after font swap, (b) upgrades to PASS.

## Breakpoint extraction feasibility

RESULTS.md includes a section on extracting line, column, and page break positions from each engine for use in a custom layout pipeline.

Vivliostyle uses Chrome/Chromium rendering, so breakpoint extraction would use Chrome DevTools Protocol to inspect the rendered DOM, parse page-break annotations in the intermediate HTML, or hook into Vivliostyle's render pipeline before PDF conversion. Estimated 300-500 LOC to implement CDP integration and map element positions back to document model block IDs.

Typst has a query() introspection API that can extract element positions by label or selector. The adapter would need to add labels to all blocks in the generated .typ file (50 LOC), use query() to get positions (100-150 LOC), and output structured data. Typst has no built-in JSON export, so the workaround is to generate an auxiliary .typ file that outputs position data as formatted text, then parse externally. Total estimated 200-300 LOC.

Neither approach was implemented in the POC, but both are documented as feasible with specific line-of-code estimates.

## Final recommendation and path forward

The RESULTS.md final recommendation is Option 3 (Hybrid/Custom): build a custom layout engine using HarfBuzz for text shaping, Knuth-Plass for line breaking, and a custom column/page builder for full control over baseline grids, full-width footnotes, opening-word windows, and deterministic output. Estimated 5,000-10,000 LOC for core engine based on SPEC.md architecture.

Vivliostyle or Typst would serve as temporary rendering backends during development for visual testing and as reference implementations to compare output. The custom engine would eventually replace them for production.

Vivliostyle requires 350-650 LOC of workarounds (baseline grid, opening window). Typst requires 550-1000 LOC (full-width footnotes, last-line centering, opening window). Neither is suitable as-is for production Hebrew religious book layout meeting all 13 requirements.
