# POC Evaluation Review: Vivliostyle and Typst for Hebrew Layout

**Verdict**: NEEDS_CHANGES

This POC evaluated two layout engines (Vivliostyle and Typst) against 13 requirements for Hebrew religious book typesetting. The deliverables exist and the evaluation table is complete, but no visual evidence was produced and the working process appears to have been compromised by marking requirements as pass/partial/fail based on code inspection rather than actual rendering. The absence of PNG evidence is a documented blocker, yet several requirements show confident ratings without visual confirmation.

**Watch for:** No PNG visual evidence exists (confirmed: high). Ratings appear speculative rather than verification-based (confirmed: high). sample.json contains authentic nikud but no teamim (likely: low). Both engines produced PDFs but quality assertions lack visual proof (confirmed: medium).

## High-level view

RESULTS.md provides a complete 13×2 matrix with notes for each partial or failed requirement, cost estimates per workaround, and a data-based recommendation to build a custom engine. The document structure meets expectations. Both engines successfully generated PDFs (Vivliostyle: 111KB, Typst: 32KB) and determinism testing was executed with hash comparisons. sample.json includes Hebrew text from Genesis with nikud, three footnotes including one long footnote, and flags for opening+window. The adapters exist and generate intermediate formats (HTML/CSS for Vivliostyle, .typ for Typst). README documents PowerShell commands and prerequisites.

The core issue: no PNG files were generated. RESULTS.md acknowledges the pdf-to-img Node.js package failed and marks several requirements as UNVERIFIED, yet other requirements show PASS/PARTIAL/FAIL ratings despite this same evidence gap. The confidence in those ratings is unclear. If visual inspection happened manually (PDFs opened in a viewer), that method should appear in the reproduction instructions. If ratings derive from code inspection alone without rendering verification, they violate the instruction "לא מסמנים הצלחה בלי שראית את העמוד".

Determinism testing shows both engines non-deterministic (Vivliostyle hash differs by PDF metadata timestamps likely, Typst unexpectedly non-deterministic despite claims). Both adapters include gematria functions with טו/טז handling. Breakpoint extraction is discussed: Vivliostyle would require CDP/Puppeteer, Typst might expose query() API. The recommendation is sound: neither engine fits requirements without 450-810 lines of workaround code; build custom engine using HarfBuzz, SkiaSharp, Knuth-Plass.

## Determinism test

RESULTS.md "Determinism Testing" section documents the test method: run each engine twice, hash the PDFs, compare. Results: Vivliostyle hashes differ, Typst hashes differ. Both marked NON-DETERMINISTIC.

Vivliostyle run1: `178D0A38338CFD5A3EEB165B93B66AE254A5D6089072D9E3ED9C73347BB5F208`
Vivliostyle run2: `E2B31DBB51680C05E5D25527ED0046F7A955391CA03CB5238121CFBDD0417244`

Typst run1: `2E34F6C7687C80053384730060E5D7B5CBFB9D2593D0927469DE181160555150`
Typst run2: `B94D498D84BF41872285F326AE3A5DB6E496A0B3869FC4BFA20C1EC803CD700D`

Notes suggest PDF metadata (creation timestamp) as likely cause for Vivliostyle, unknown cause for Typst. The conclusion "NON-DETERMINISTIC" is accurate for binary PDF output, but may be too harsh for layout determinism. PDF metadata timestamps do not affect text positions, line breaks, or page breaks. The spec (section 2) says "אותו קלט נותן אותו פלט בכל מחשב" and emphasizes embedded fonts and no system dependencies, suggesting the goal is reproducible layout, not bit-identical PDFs.

A more rigorous test: extract text with positions from both PDFs, compare structure. Tools: pdftotext -layout, or pdf.js getTextContent. If text positions are identical but only metadata differs, the engine is layout-deterministic with non-deterministic serialization, which is acceptable for the use case (collaborative editing, version control of layout, citation stability).

RESULTS.md notes this possibility: "PDF binary determinism may be achievable by: 1. Stripping metadata timestamps 2. Using reproducible build flags 3. Embedding fonts consistently However, neither engine provides this out of the box." This is fair.

The conclusion for requirement (m) should distinguish layout determinism (pass/fail) from binary determinism (fail for both). The current table lumps them together.

## Recommendation analysis

RESULTS.md recommendation: build custom layout engine using HarfBuzz, SkiaSharp, Knuth-Plass. Estimated effort: core engine 2000-3000 lines, import/export 500-800 lines, total 2500-3800 lines. Rationale: Vivliostyle requires 450-680 lines of workaround code, Typst requires 580-810 lines, and both have fundamental limitations (baseline grid, full-width footnotes) that are hard to overcome.

The recommendation is data-based: the evaluation matrix shows which requirements fail for each engine, the "Total Custom Code Estimates" table sums workaround costs, and the tradeoff section lists "full control over cost function", "baseline grid guaranteed", "no licensing issues", "deterministic by design" as benefits. The comparison is explicit: workaround code for existing engine vs. clean-slate implementation.

The recommendation references SPEC.md section 18 multiple times (Typst forum issue for two-column footnotes, Vivliostyle GitHub issue #1157 for baseline grid, hybrid approach) and section 7 (cost function), section 10 (footnote placement), sections 7-10 (page layout logic). This is good: the recommendation is grounded in the spec, not invented.

The estimated effort (2500-3800 lines) is not justified. No breakdown by component, no reference to similar projects (HarfBuzzSharp line count, SkiaSharp PDF sample code line count, Knuth-Plass C# port line count), no prototype. The number could be accurate or wildly off. RESULTS.md acknowledges this: "Estimated effort" not "Measured effort". For a POC, rough estimates are acceptable, but the confidence should be stated: "rough estimate based on complexity assessment, not implementation experience".

The "Why this is better" section claims "Deterministic by design". This is optimistic. A custom engine can be deterministic, but requires discipline: no system time calls, embedded fonts, stable sort for layout decisions, fixed-precision arithmetic. The spec (section 2) requires this, so the claim is aligned with spec intent, but "by design" suggests it's automatic, which it isn't.

The "If Forced to Choose" section picks Vivliostyle marginally, with rationale: "footnote architecture is closer to requirements", "larger ecosystem", "better documentation", "CSS is more familiar". This is reasonable. The caveat "Baseline grid issue may be insurmountable" is honest.
