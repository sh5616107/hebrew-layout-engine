# Hebrew Layout Engine POC Review

Comprehensive evaluation of Vivliostyle and Typst engines against 13 requirements for Torah book layout.

## Summary

The POC successfully generated PDFs from both engines and produced PNG evidence files for visual verification. Both engines show partial capability but neither meets all requirements out of the box. The deliverable includes authentic Genesis text with nikud from Mechon-Mamre, detailed requirement-by-requirement analysis, and quantified workaround estimates.

**Watch for:**
- **Unverified claims (likely)**: RESULTS.md marks 10+ requirements as "UNVERIFIED" without completing visual verification against PNG files. This means pass/fail ratings cannot be confirmed.
- **Missing multi-page evidence (confirmed)**: Single-page sample cannot test footnote continuation (req j), running headers (req k), or column balancing (req d). These are marked N/A rather than tested.
- **Baseline grid claim not verified (likely)**: Vivliostyle marked FAIL for requirement (e) based on GitHub issue #1157, but no PNG overlay measurement confirms the claim for this specific output.
- **Opening window implementation broken (likely)**: Typst adapter implementation uses `place()` which removes content from flow rather than creating wrap-around. The PDF likely shows broken layout but wasn't verified.

**Verdict**: NEEDS_CHANGES

## High-level view

The POC establishes that neither engine is production-ready but provides data-based evidence for the decision. PDF outputs exist for both engines, PNG conversions succeeded, and the sample uses authentic public-domain Torah text, meeting honesty requirements. However, the evaluation stopped short of completing visual verification: most requirements are marked "UNVERIFIED" with notes like "PNG available, manual measurement needed" or "requires manual inspection." This means the ratings table presents implementation status, not verified behavior. The determinism requirement correctly identifies PDF metadata timestamps as the cause of hash mismatches. Workaround estimates (350-650 LOC for Vivliostyle, 550-1000 LOC for Typst) provide quantitative decision support. Font selection used Windows system font "David" with documented limitations on teamim coverage, and alternative fonts are recommended.

The single-page sample design is a structural gap: three requirements (footnote continuation across pages, running header odd/even differentiation, final column balancing) cannot be tested without multi-page content, yet they're marked "N/A" rather than addressed with expanded sample data. The opening window implementation in Typst appears broken based on code review—the adapter uses `place()` which doesn't create text wrap-around—but the PDF wasn't inspected to confirm.

RESULTS.md includes references to external documentation (GitHub issues, forum threads) that substantiate engine limitations. The recommendation to build a custom engine is backed by comparative LOC estimates and cited SPEC.md sections. The document structure matches the requirement: table covering all 13 requirements, notes explaining workarounds and costs, and a data-based recommendation at the end.

## Deliverable completeness

RESULTS.md exists and contains the required structure: a table covering all 13 requirements (a through m), ratings for both Vivliostyle and Typst on each requirement, and notes explaining what was tried and what workarounds would cost. The document ends with a clear recommendation: build a custom layout engine because both engines require 350-1000 LOC of workarounds.

The evidence files are present: `vivliostyle-page-1.png` (284,083 bytes) and `typst-page-1.png` (287,049 bytes) were successfully generated from the PDFs. Both PDFs exist (`vivliostyle.pdf` at 24,687 bytes, `typst.pdf` at 36,819 bytes), along with determinism test files (run1, run2 for each engine). README.md contains PowerShell commands for reproduction. The `sample.json` file includes authentic Genesis 1:1-10 text from Mechon-Mamre with nikud marks (U+05B0–U+05C7 range visible in the JSON) and teamim marks (visible as characters like ֽ֖֣֑֥֖֥׃). The longest footnote (note-3) is approximately 150 words discussing the meaning of "rakia" with multiple Rabbinic sources, meeting the "long footnote" requirement for testing continuation.

Adapters `to-html-css.js` and `to-typst.js` both read `sample.json` and transform to engine-specific formats. Both implement gematria conversion with טו/טז special cases, opening word handling, and footnote references. Engine-specific limitations are documented in code comments: Vivliostyle has "VIVLIOSTYLE-LIMITATION: Baseline grid alignment between columns is not fully supported" and Typst has "TYPST-LIMITATION: Centering only the last line of a paragraph is not directly supported."

## The unverified gap

Requirement (b) nikud rendering: "PARTIAL... requires manual inspection of teamim quality." Requirement (c) two equal columns: "UNVERIFIED... requires manual column width measurement." Requirement (e) baseline grid for Vivliostyle: "FAIL (confirmed limitation)" but then notes "requires grid overlay measurement to confirm." Requirement (f) opening window: "UNVERIFIED (requires visual verification)" for Vivliostyle. Requirement (h) footnotes: "UNVERIFIED... requires manual inspection of footnote placement and width."

The PNG files exist, meaning visual verification is possible, but the review stopped at generation. The RESULTS.md document reads more like a test plan than a test report: "check this manually," "measure that on screen," "verify with grid overlay." Most cells describe implementation intent rather than confirmed behavior.

The document status line says "Evaluation complete, visual verification pending PNG generation." But the PNGs were generated successfully, so the status line is outdated.

## Single-page sample structural gap

Three requirements are marked N/A because the sample content fits on a single page: requirement (d) column balancing, requirement (j) footnote continuation across pages, and requirement (k) running headers with odd/even differentiation.

The requirement was to test all 13 criteria, and three of them require multi-page content by definition. The POC cannot answer whether Vivliostyle or Typst correctly handle footnote continuation (requirement j is mandatory per SPEC.md), which is a critical feature for Torah book layout.

Both adapters implement running header logic: Vivliostyle uses `@page :left` and `@page :right` with counter styles, Typst uses `header: context { if calc.odd(here().page()) }`. Without multi-page output, these code paths are unexecuted and unverified.

## Typst opening window implementation

The Typst adapter attempts to implement the opening window (requirement f: first words bold with empty space below) using `place(top + right, float: true)` wrapping a box of calculated height. Typst's `place()` function positions content without affecting flow, similar to CSS absolute positioning, so the adapter's approach cannot work as intended. The RESULTS.md marks this as "FAIL (compilation likely broken)" and notes the evidence file "likely shows broken layout or no window." But the PDF was successfully generated (36,819 bytes), so it didn't break compilation. What the PDF actually shows is unknown because the visual verification wasn't completed.

The Vivliostyle adapter uses a CSS float approach: wrap opening words in a span with `float: inline-start`, set `height` to `(windowLines + 1) × baseline grid`, and let text wrap around the floated box. This is marked "UNVERIFIED" with 23 LOC added, but no visual confirmation.

## Baseline grid alignment claim

RESULTS.md marks Vivliostyle as "FAIL (confirmed limitation)" for requirement (e) baseline grid alignment and cites GitHub issue #1157: "Baseline grid alignment between columns is not fully supported." But the document then notes "Evidence: poc/out/vivliostyle-page-1.png (requires grid overlay measurement to confirm)." This creates uncertainty: is it marked FAIL because the issue exists in principle, or because the PNG shows misalignment in this specific output? The distinction matters because uniform line-height might be sufficient in simple cases even if the engine lacks general baseline-grid support.

Typst is marked "UNVERIFIED... requires grid overlay measurement for verification" for the same requirement. The asymmetry is notable: Vivliostyle is failed based on a known issue without confirming the specific output, while Typst is left unverified despite having no known issue cited.

## Determinism testing

Both engines are marked FAIL for requirement (m) deterministic output. The test was executed correctly: vivliostyle-run1.pdf and vivliostyle-run2.pdf were generated, SHA256 hashes compared, and found to differ. Same for Typst. The document correctly identifies the cause (PDF metadata) and suggests workarounds (strip metadata before comparison, or compare visual content only, estimated 50-100 LOC).

## Font selection and teamim concern

The sample uses "David" font (Windows system font) with documented limitations: "David font has nikud support but limited teamim coverage." Alternative fonts are recommended (Ezra SIL, Taamey David CLM) with license information and download links.

The sample.json text includes teamim marks like ֖ (tipeha), ֣ (munah), and ֑ (etnachta). Whether these render correctly in the PNG files is unknown without visual inspection, which is why requirement (b) is marked PARTIAL rather than PASS or FAIL.

## Workaround estimates and recommendation

RESULTS.md quantifies the cost of using each engine: Vivliostyle would require 350-650 LOC of custom code (200-400 for baseline grid workaround, 150-250 for window implementation). Typst would require 550-1000 LOC (300-500 for full-width footnotes, 150-300 for last-line centering, 100-200 for window).

The recommendation is to build a custom layout engine using HarfBuzz for text shaping, Knuth-Plass for line breaking, and custom column/page builder for full control. Estimated effort: 5,000-10,000 LOC. The document cites SPEC.md architecture and notes ROI: full control over all requirements, no ongoing workarounds, deterministic output.

The data includes many unverified claims, so the confidence in the recommendation is lower than it appears.



## Evidence file integrity

All required files are present and non-empty. The fact that run1 and run2 PDFs have identical file sizes (24,645 bytes for Vivliostyle, 36,602 bytes for Typst) but different hashes confirms that the difference is in metadata, not gross structural changes.

## Breakpoint extraction analysis

RESULTS.md includes a section on breakpoint extraction feasibility (not part of the 13 requirements but mentioned in the task's step 5). For Vivliostyle: "POSSIBLE but requires custom integration" using Chrome DevTools Protocol, estimated 300-500 LOC. For Typst: "POSSIBLE with Typst introspection API" using `query()` and `locate()`, estimated 200-300 LOC but notes "Typst doesn't have built-in JSON output." The estimates are in the same LOC range as the workarounds, which supports the recommendation that neither engine saves enough implementation cost to justify their limitations.

## Honesty and integrity

The document does not mark any requirements as PASS without evidence. Where implementation exists but verification is pending, it says "UNVERIFIED." Where the sample is insufficient to test, it says "N/A." Where an approach failed, it says "FAIL" and explains why. The sample.json uses authentic public-domain Torah text from Mechon-Mamre, not fabricated content.

The determinism requirement is marked FAIL even though the layout might be deterministic (the variation is in metadata). A less honest evaluation could have marked this PARTIAL or argued that "deterministic layout" is what matters.

## README.md reproduction instructions

The README provides step-by-step PowerShell commands for running the POC: generate layout files with Node.js adapters, build PDFs with Vivliostyle CLI and Typst, view results, optionally generate PNGs with ImageMagick or Poppler, and test determinism with hash comparison. Prerequisites are listed with version numbers.

The README includes a troubleshooting section addressing common issues including network blocking, which correctly states "per project requirements, STOP and report" with explicit instruction not to bypass filtering, matching the task specification.

The task asked to test all 13 requirements, and (l) is one of them. As written, it's an incomplete evaluation of a stated requirement rather than a justified scope reduction.
